# 备份与恢复

对应 #45、REQ-007/009、[ADR-0005](../adr/0005-data-consistency.md)、[ADR-0014](../adr/0014-neon-databases.md)。本文写 staging 的做法；生产库由 #52 创建，按同样的方式接入，用自己的密钥、变量和 artifact 名。

## 目标

| 项目     | 目标                                                     | 做法                                                                                      |
| -------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 备份     | 每日加密备份，独立存储，保留 14 天                       | `staging-backup` 每天 19:41 UTC（北京时间 03:41）运行，存为 GitHub Actions artifact       |
| RPO      | 普通业务数据最多丢失 24 小时；已受理的家庭删除一个不丢   | 每日备份；删除清单在另一个 Neon 项目里，不进备份，恢复时整份重放                          |
| RTO      | 从决定恢复到检查通过、重新开放，4 小时内                 | `staging-restore` 一次运行完成，分步计时；实测见 [#45 验收记录](../evidence/45/README.md) |
| 删除清单 | 条目保留到所有可能含有该家庭的可恢复备份都已过期才能销毁 | 每小时维护删去完成已超过 15 天的条目；未完成的条目一直保留                                |

## 备份里有什么

- 应用库的 `pg_dump`（custom 格式，不含属主和授权），以及一份清单：来源环境、来源主机、快照时间、dump 的 SHA-256、快照里每张表的行数。行数和 dump 读的是同一个导出快照。
- 服务开关表 `service_gate` 的结构，不含它的那一行：恢复出来的库因此一开始是关闭的，见 [staging 服务开关](staging.md#服务开关)。
- 不含删除清单库。清单只有内部家庭 ID 和时间，它的作用正是在恢复后清掉备份里已删除的家庭，放进应用库的备份就失去意义。
- 服务开关关闭时不备份：这时库正在恢复，或恢复没有通过检查。

## 存放位置与权限

| 副本                | 位置与保留                                                                                              | 谁能读                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 每日备份            | GitHub Actions artifact `staging-backup`，`retention-days: 14`，到期由 GitHub 自动删除                  | 仓库公开，任何登录 GitHub 的用户都能下载这个文件；文件用 age 加密，只有持有私钥的人能解开 |
| Neon 自带的恢复历史 | 两个 Neon 项目各自的历史窗口，Free 为 6 小时                                                            | 能登录维护者 Neon 账号的人                                                                |
| 运行时的临时文件    | GitHub 托管 runner 的 `$RUNNER_TEMP`，加密前的 dump 在加密后立即删除，恢复结束时清理；runner 用完即销毁 | 只在本次运行内                                                                            |
| 手工导出            | 默认没有。确需手工导出时，记在 #45 验收记录里，14 天内删除                                              | 导出的人                                                                                  |
| 加密私钥            | `staging` environment 的 secret `STAGING_BACKUP_IDENTITY`，另由维护者离线保存一份（如密码管理器）       | 维护者；恢复工作流在运行时读取。只有仓库写权限的人能手动运行恢复                          |
| 加密公钥            | Repository variable `STAGING_BACKUP_RECIPIENT`                                                          | 公开无妨，只能加密                                                                        |

备份和 Neon 在不同的供应商：Neon 项目整个丢失时，备份仍在 GitHub。私钥丢失时现有备份都无法解开，需要生成新密钥，旧备份视为不可用，直到 14 天后自然过期。

## 首次设置

1. 安装 age：Windows 运行 `winget install FiloSottile.age`，macOS 运行 `brew install age`。
2. 生成密钥：`age-keygen -o staging-backup-key.txt`。屏幕上打印的 `Public key: age1…` 是公钥；文件里 `AGE-SECRET-KEY-1…` 那一行是私钥。
3. 在 [Actions variables](https://github.com/juanchaopan/education/settings/variables/actions) 新建 Repository variable `STAGING_BACKUP_RECIPIENT`，值为公钥 `age1…`。
4. 在 Settings → Environments → `staging` → Environment secrets 新建 `STAGING_BACKUP_IDENTITY`，值为私钥那一行 `AGE-SECRET-KEY-1…`。
5. 把 `staging-backup-key.txt` 存进密码管理器或其他离线位置，然后从电脑上删除。不要发到聊天，不要放进仓库。
6. Neon 项目的 PostgreSQL 版本不是 17 时，新建 Repository variable `STAGING_POSTGRES_MAJOR` 写上主版本号；备份和恢复用的客户端工具必须和服务器主版本一致。
7. 在 Actions → staging-backup → Run workflow 运行一次，确认生成了 `staging-backup` artifact。

## 依次运行

发布、每日备份、恢复和每小时维护各自在运行期间持有应用库上的同一把 PostgreSQL advisory lock，后到的最多等 10 分钟，所以它们不会同时改动或读取 staging 数据库。这把锁跟着数据库会话，恢复替换 schema 时仍然有效；runner 中途退出时会话断开，锁随之释放。

## 恢复

在 Actions → staging-restore → Run workflow 运行。`backup_run` 留空时恢复最近一次成功的备份；要恢复更早的备份，填那次 `staging-backup` 运行的 ID（运行页面地址里 `/runs/` 后面的数字）。

工作流依次：

1. 下载并解密备份，核对来源环境是 staging、dump 与清单里的 SHA-256 一致、备份不超过 14 天。不符合时退出，不改动任何数据。
2. 取得数据库锁，关闭服务开关。从这一步起，任何失败都让服务保持关闭，网站显示维护中。
3. 删掉应用库的 `public` 和 `drizzle` 两个 schema，在一个事务里载入 dump。
4. 核对载入的服务开关是关闭的，每张表的行数与清单一致。
5. 迁移到当前版本并做 staging 加固，确认当前版本的迁移已完成。迁移不碰服务开关。
6. 在一个事务里删除备份中还有、删除清单里记着的每个家庭（不论这条删除当时是否已完成），并撤销所有家长和孩子的会话；再清除已经过期的草稿。之后才过期的草稿，读取时同样不可见，由每小时维护清除。
7. 再读一遍删除清单，库里没有清单里的家庭，才打开服务开关。
8. 打印每一步的耗时、撤销的会话数和备份的数据时点，写进运行摘要。

恢复后所有家长和孩子都要重新登录：备份之后退出或被撤销的会话不会因此复活。失败后网站保持维护中。看工作流日志里的原因，处理后重新运行；也可以换一份备份运行。恢复不能撤回：旧库的数据在第 3 步已被替换。

### 恢复到新的 Neon 项目

Neon 项目整个不可用时：按 [staging 一次性配置](staging.md#一次性配置) 新建项目，更新 `STAGING_DATABASE_URL` 和 `STAGING_DATABASE_HOST`，运行 `staging-restore`，再手动运行 staging 发布，让 Vercel 运行时拿到新的连接串。发布之前，线上版本仍连着旧库。

删除清单库不可用或无法证明完整时，不恢复应用库：恢复会让清单之后删除的家庭回来。先用 Neon 的恢复历史找回清单库（6 小时内），找不回时保持关闭，由维护者决定。

### 不用 Neon 的恢复功能回退应用库

Neon 的 instant restore 会把应用库连同服务开关一起退回到过去的时点，那之后删除的家庭会直接回来，不经过清单重放。需要回退应用库时，使用 `staging-restore`。Neon 的恢复只用于找回删除清单库。

## 删除清单的保留与销毁

- 每次恢复都重放整份清单，所以清单必须覆盖所有还能恢复的备份。备份最多 14 天，Neon 恢复历史 6 小时；清单条目在删除完成 15 天后由每小时维护删去，打印删去的条数。
- 恢复拒绝超过 14 天的备份，即使 artifact 还在。
- 未完成的删除不删条目，直到维护把它完成。

## 限制

- 恢复只能回到备份的时点：备份之后改过的家长密码和孩子 PIN 会变回旧值。恢复后需要提醒在那之后改过密码或 PIN 的家庭再改一次。
- GitHub 的定时任务可能延迟，备份的实际间隔会略超过 24 小时；RPO 以恢复时打印的备份时点为准。
- 公开仓库 60 天没有任何提交时，GitHub 会停用定时工作流，包括备份。届时需要在 Actions 页面重新启用。
- 备份由 GitHub Actions 读取 staging 的数据库秘密。能修改工作流的人就能读取这些秘密，这和发布流程一样。
- 只备份 staging。生产库在 #52 创建，接入时使用独立的密钥对、变量和 artifact 名，不能把生产备份恢复到 staging：恢复会核对备份的来源环境。
