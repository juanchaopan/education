# 视觉基准与可访问性检查

界面外观由经维护者评审的截图基准固定，可访问性由同一套测试自动检查。目标见 [架构总览的视觉验证](../architecture/overview.md#视觉验证已确认) 和 [ADR-0003](../adr/0003-web-details.md)。

## 固定环境

截图取决于浏览器版本和系统字体，所以测试只在官方 Playwright 镜像里运行：`mcr.microsoft.com/playwright:v<版本>-noble`，版本号取自 `package-lock.json` 里安装的 `@playwright/test`。镜像固定了 Chromium 和字体；正文中文由镜像自带的文泉驿正黑（WenQuanYi Zen Hei）渲染，标题用构建时生成的霞鹜文楷子集（见 [网站视觉语言](visual-language.md#字体)）。文字一律用灰度抗锯齿（Chromium 的 `--disable-lcd-text`）：否则 Chromium 只在不透明的图层上用彩色的次像素抗锯齿，同一段文字的样子就取决于页面当时怎样分层。升级 Playwright 会换镜像，基准要随之重新生成并评审。

本地和 CI 运行的是同一个命令 `npm run test:visual`（`scripts/visual.mjs`）：把仓库复制进容器（不带 `node_modules` 和构建产物），在容器里 `npm ci`、构建应用和 Storybook，再运行 `playwright.visual.config.ts`。本机需要 Docker 正在运行；复制进容器时仓库里的文件不能正在改动，否则复制会失败。本机的 `node_modules` 不会被改动，写回的基准和测试结果归仓库的所有者。环境变量 `CI` 会传进容器，CI 里因此禁止 `test.only`。所有视口按 1 倍像素截图，基准只用来发现布局、换行和颜色的变化。

同一份代码每次截出的图都逐像素相同，所以 CI 里失败的测试会重试一次，但重试后才通过（flaky）也算失败：重试只用来看出是两次都失败还是只失败一次，不能让偶发的差异混过去。

`--` 之后的参数原样交给 Playwright，例如用 `npm run test:visual -- -- --grep 孩子登录` 只比对部分测试，在内存紧张时用 `-- -- --workers=2` 减少同时打开的浏览器，或用 `-- -- --grep <名字> --repeat-each=20` 检查一张截图是否每次都相同。

## 截图前的条件

截图要等页面画完最终的样子，而且截出的图只取决于最终的页面，不取决于页面是按什么顺序、在哪一帧画出来的。`visual/render.ts` 和 `visual/pages.ts` 里的辅助函数逐条保证下面的条件；新的截图测试也要满足它们，截图统一经 `expectScreenshot` 截取。

| 条件       | 做法                                                                                                                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 时间和主题 | 打开页面前固定时钟（`fixClock`）：白天主题取 2026-11-07 10:00，晚上主题取 20:00（北京时间），主题在第一次绘制前就选好；截图前确认 `<html>` 的 `data-theme` 是要截的主题                                              |
| 数据       | 每个 `/api` 请求按表固定回答；等到状态的标题出现，有 `pressable` 的等按钮可以按，有 `last` 的等最后到达的文字出现                                                                                                    |
| 不动       | 打开页面前加一张样式表（`holdStill`），把所有 CSS 动画和过渡的时长、延迟设为 0：有限的动画直接停在最后一帧，循环的动画停在静止的样子。截图前确认没有正在运行的动画（`expectScreenshot`），脚本启动的动画会让测试失败 |
| 图片和字体 | 立即加载的 `<img>` 图片都已加载并解码，`document.fonts.ready` 已完成；作为 CSS 背景的图片不在其中，晚到时截图会变，测试按不稳定失败（`waitForPicturesAndFonts`）                                                     |
| 重新绘制   | 一切就绪后把整页重新排版、从头绘制一遍，等这次绘制上屏再截图（`expectScreenshot`）；原来有焦点的元素重新获得焦点                                                                                                     |
| 语言和时区 | zh-CN，Asia/Shanghai                                                                                                                                                                                                 |

后两条针对的是浏览器只重绘变化部分的做法。数据分几次到达时，页面先画出一部分，后到的数据只让相关的部分重画；各自成层的部分（例如晚上主题里带背景模糊的卡片）保留着周围排版还在变化时画的内容，那时画的文字和色块可能与之后画的差一像素。比如平板晚上的家长空间总览，“AI 老师”一行的授权状态最后到达，这一行就会随请求到达的先后上下差一像素。动画也一样：动画进行时画出的内容取决于动画走到哪一帧，只在截图那一刻停下动画不够。整页重画、动画从第一帧起就不动，截图就只取决于最终的页面。只有截图测试这样做（同一测试里截图后的 axe 也在不动的页面上运行）；`accessibility.spec.ts` 的键盘、减少动画、触摸和缩放检查看的是网站真实的动效。

## 覆盖范围

每个截图在桌面（1280×720）、平板（iPad 810×1080）和手机（iPhone 13 390×664）三个视口各有一张基准，放在 `visual/<测试文件>-snapshots/<视口>/`。

| 测试                    | 内容                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stories.spec.ts`       | Storybook 里的每个 story：各组件的正常、空、加载中、失败、长文字和“再听一遍”等状态。截图后对 story 运行 axe                                                                                                                                                                                                                                          |
| `pages.spec.ts`         | 关键页面的整页截图：题库的空、加载中、失败和长标题，题目不可用，题目的片名卡，家长空间未登录、会话出错、注册关闭和邮箱待验证，家长空间总览（有两个孩子、还没有孩子）和孩子、练习安排、学习记录、隐私与数据四个分区，练习安排的书库、我的家庭、一个孩子的书架、第一次加载、没打开和还没有孩子，孩子登录，孩子注册，找回密码，两个缺少链接的页面和 404 |
| `accessibility.spec.ts` | 键盘、减少动画、触摸和缩放，见下文                                                                                                                                                                                                                                                                                                                   |

网站白天、晚上各有一套主题。所有 story 和页面都有白天的基准；关键部件和关键页面另有一张晚上的基准，文件名带 `--night`（story）或 `-night`（页面），axe 和可访问性检查对两套主题都运行：

- 部件：主按钮、次按钮、危险按钮、图标按钮、卡片、输入框、下拉选择、三种提示条、空状态、加载、开关、图标总览、书卡（我的家庭、暂时不可用、默认封面）和已安排的安排按钮，名单在 `visual/stories.spec.ts` 的 `nightStories`。
- 页面：题库空状态、孩子登录、家长未登录、家长空间总览、练习安排的书库和我的家庭、题目片名卡和 404，名单在 `visual/pages.ts` 的 `nightPages`。

页面测试不连数据库：每个 `/api` 请求都由测试按 `visual/api.ts`、`visual/parent-space.ts`、`visual/bookshelf.ts` 和 `visual/pages.ts` 里的表固定回答，表里没有的请求会让截图测试和可访问性检查都失败。长标题、长邮箱、长昵称和家长空间里的题目和书等只是测试夹具，不进入题目清单。story 的主题由地址里的 `globals=theme:night` 选择。

## 可访问性检查

| 方面        | 检查                                                                                                                                                                                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| WCAG 2.2 AA | 每个 story 和每个页面运行 axe（`wcag2a`、`wcag2aa`、`wcag21a`、`wcag21aa`、`wcag22a`、`wcag22aa`），含对比度、名称和标签、链接不只靠颜色区分                                                                                                                   |
| 键盘        | 桌面视口逐个按 Tab：每个控件都能到达（一组单选按钮算一站），焦点处有至少 2px 的轮廓；第一站是“跳到主要内容”，按回车后焦点到主要内容                                                                                                                            |
| 减少动画    | 打开减少动画偏好后，页面上没有任何动画或过渡                                                                                                                                                                                                                   |
| 触摸        | 平板和手机视口里每个控件的宽和高都不小于设计令牌 `--touch-target`，也不小于 44 CSS 像素；包在标签里的控件量标签，句子里的链接按 WCAG 的行内目标豁免，独占一行的链接用 `StandaloneLink`。点按可以打开家长登录、经品牌回到首页进入孩子空间、拨动孩子的“记住”开关 |
| 缩放        | 320 CSS 像素宽（相当于 1280 屏幕放大到 400%）不横向滚动；640 像素宽、文字放大到 200% 时不横向滚动                                                                                                                                                              |
| 不只靠颜色  | 告诉孩子或家长结果的状态（画板的区域反馈、AI 老师的反馈、没听清、声音没出来、PIN 或登录错误、KEY 无效）在状态或提示区域里有文字                                                                                                                                |

## 更新基准

基准不会被普通运行写入：配置里 `updateSnapshots: 'none'`，缺少或不同的基准都让测试失败。比对允许每张图最多 20 个像素不同（`maxDiffPixels`），这只是余量，截图本身每次都应逐像素相同。外观有意改变时：

1. 运行 `npm run test:visual -- --update`。它运行全部测试、重新生成 `visual/*-snapshots/` 下的全部基准，已不存在的 story 或页面的旧基准随之删除。因为会整体替换基准，它只接受 `-- --workers=<n>`，不接受 `--grep` 之类的筛选。
2. 用 `git status` 和 `git diff --stat` 看哪些图变了，逐张对照新旧图；改动和代码放在同一个 PR。没有改到的页面或组件的图也变了，说明截图不稳定：找出原因并让它满足上面的截图条件，不要只把图还原。
3. PR 里写明哪些页面或组件的外观变了。`*-snapshots/**` 属于高风险路径，由维护者看过图后加 `human-reviewed`。

CI 的 `visual` job 失败时，下载 `visual-diff` 产物：每个失败的截图都有基准图、实际图和差异图。本地运行失败时，同样的文件在 `test-results/visual/`。

## 不能由截图代替的检查

截图和自动检查不能代替真实设备：手机和平板上的真实触摸、系统缩放、屏幕阅读器朗读、麦克风和声音，需要在真机上补充确认。主题按时间切换时的过渡观感、页面和动画的动效、大陆网络下字体的加载时间，也要在真机上确认。
