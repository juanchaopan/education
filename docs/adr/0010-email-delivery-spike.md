# ADR-0010 有条件采用 Gmail 作为试点发信方案

- 状态：已接受试点实现方向；当前条款/额度、正式失败恢复与生产验收仍为上线前门槛
- 日期：2026-11-04
- 相关需求：REQ-002、REQ-007、REQ-009
- 任务：[#16](https://github.com/juanchaopan/education/issues/16)
- 证据：[探针记录与限制](assets/0016-email-evidence.md)

## 背景

最多 10 家庭的试点需要家长注册验证与密码恢复邮件。维护者选择普通 `@gmail.com` 账号作为候选，指定只测试 126.com；两类邮件均确认进入正常收件箱，速度描述为“very fast”，两封邮件中的测试网站链接均能打开。维护者随后询问剩余事项并要求收尾。本 ADR 接受有条件的试点方向，不将其表述为完整生产验收。

#16 的调查结束不等于原始验收项全部通过。当前 Google 条款/额度正文在环境代理处被拒绝，真实故障恢复亦未验证。原验收缺口保留并交接到 #20、#21、#22、#51、#52；不能凭两封收信推定持续免费、全大陆可用或满足精确延迟目标。

## 候选方案

| 方案                               | 已有证据与代价                                                                           | 结论                                   |
| ---------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------- |
| 个人 Gmail + Nodemailer / TLS SMTP | 实际 Vercel 连接/授权及两类 126 收信获维护者确认；需管理应用密码、共享账号额度和风控中断 | 有条件用于试点                         |
| Gmail API + OAuth                  | Google 官方 discovery / 样例提供发送接口；授权、刷新与审核规则和实际投递未验证           | 应用密码路径不可用时再评估，不自动切换 |
| Resend / Brevo                     | 官方 Node SDK 说明 HTTP 发信接口；当前免费套餐、身份/域名规则与国内投递未全部核实        | 保留备选，不标为已验证或已采用         |

来源是固定版本代码资料、控制台/API 元数据、本机检查和用户回传，分别标注。未开通付费邮件服务；不引用凭记忆得到的免费数字。

## 决策

1. 正式实现从服务端邮件适配器接入 Gmail，Node.js 24 与 TypeScript 7 保持不变；探针使用 `nodemailer@10.3.1`，正式实现时复核版本和依赖。应用服务生成验证/恢复意图，供应商适配器负责投递，便于迁移。原型代码、依赖与管理员测试页面不合入正式应用。
2. 使用专用个人 Gmail 地址作为 From，应用专用密码保存在隔离服务端秘密配置中，TLS 465 验证证书、TLS1.2+；不使用普通 Google 登录密码，不进入浏览器、仓库或日志。家长使用自己的常见邮箱，不需要 Google 登录。应用密码权限与 Google 发件箱内容留存应在接入时核实；不要将其假定为只允许发送的细粒度凭据。
3. Gmail 地址发信不要求先购买自有发信域名；不伪装成 `@hyp.app`。网站域名继续独立管理，真实账号链接使用配置的可信 HTTPS Origin，不使用请求 Host 或现有 access probe URL。自有发信域名是另一个选择，需单独核实 DNS 控制权及 SPF/DKIM/DMARC。
4. 邮箱验证 24h、恢复 30min 的随机、哈希、单次令牌沿用 [ADR-0009](0009-account-security-spike.md)。GET/HEAD 不改变账号；正式确认/重置动作按服务端授权与 CSRF 规则执行，过期/重复链接有明确恢复路径。邮件不包含儿童 PIN、家庭 KEY、学习输入或进度；不加追踪像素、链接跟踪或第三方资源。
5. 产品状态区分待发送、服务商接受、不确定结果与失败。SMTP 接受不能显示为邮箱已验证或已送达；家长完成有效单次令牌流程后才授予权限。恢复申请返回通用响应，避免泄露邮箱是否存在。
6. #21/#22 实现共享数据库限流、重发冷却、幂等和有界恢复。发送意图须持久化，不依赖函数返回后的内存任务；若用 outbox，只保留投递必需的短期受保护载荷，发送/过期后清理，不能用“令牌哈希存储”掩盖长期明文队列。重试同一有效意图不重新生成令牌，用户明确重发才撤销旧令牌。
7. 每次外部调用有超时与执行上限。显式暂时拒绝、永久拒绝、授权失效和 DATA 后丢失响应分别处理；未知送达不能盲目重试。SMTP 不提供 exactly-once 保证。实际发送方式、调度和失败恢复必须在正式 Node/Vercel/数据库环境验收，不把探针错误分类 fixture 算作恢复已实现。

## 证据与适用范围

| 样本             | 来源                               | 结果                                         | 时间的含义                                   |
| ---------------- | ---------------------------------- | -------------------------------------------- | -------------------------------------------- |
| SMTP 连接        | 维护者回传 `smtp-authenticated`    | 连接/授权成功，未发送邮件                    | 1,594ms：函数内 verify 调用耗时              |
| 注册验证测试邮件 | JSON、对应正文及“inbox, very fast” | 126 正常收件箱，中文正文可读，网站链接可打开 | 1,974ms：Google 接受邮件耗时，非实际收件耗时 |
| 找回密码测试邮件 | JSON、对应正文及“very fast, inbox” | 126 正常收件箱，中文正文可读，网站链接可打开 | 2,616ms：Google 接受邮件耗时，非实际收件耗时 |

本机 126 修订后的 12 项检查、TS7 编译/构建、lint、格式和移动布局检查通过。Vercel API 确认 Node24 / sin1 / staging READY 与默认登录保护；未读取 Gmail 密码或实际测试邮箱值。线上结果来自维护者，助手未独立重放或核对服务端日志。

收件人未提供精确收件 UTC、地区/运营商/设备。两封邮件不足以形成 P50/P95、冷启动或可用性结论；只记录“很快”。邮件中的链接打开的是既有访问探针，**没有创建账号、验证邮箱或重置真实密码**。QQ/163 不在维护者本轮范围，正式注册不因此限制为 126。

## 后果与归档

此方向解除邮件供应商未定的设计阻塞，可从 #17 的隔离适配器开始实现；不宣称正式账号邮件已经就绪。Gmail 账号可能因授权撤销、密码变动或风控中断，正式实现需有可观测的失败状态和运维恢复路径。

原型归档为 [archive/spike-16-email-delivery](https://github.com/juanchaopan/education/tree/archive/spike-16-email-delivery)，SHA `598378002feb587dcbe1f843f8c49c7041c448d4`。证据随本 ADR 合入，测试部署在收尾时退役；Google 应用专用密码由维护者从 Google 账号撤销，正式环境另配凭据。归档不包含凭据值或真实邮箱地址。

重新评估条件：账号政策/额度不适合用途、126 或目标用户邮箱持续投递失败、风控/恢复不可控、试点增长，或需要独立发信域名与更完整投递可观测性。候选切换后重新核实条款、成本与目标邮箱实测，不自动开通收费服务。
