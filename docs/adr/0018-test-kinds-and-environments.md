# ADR-0018 测试的种类和运行环境

- 状态：已接受（根据现有项目归纳）。
- 日期：2026-11-14
- 需求：REQ-002、REQ-005、REQ-007、REQ-011。
- 关系：视觉基准沿用 [视觉基准与可访问性检查](../design/visual-baselines.md)；双实例账号验证沿用 [#19](../evidence/19/README.md)。

## 背景

项目已经有单元、组件、数据库、浏览器、截图和双实例检查，但没有按种类写下来：哪种检查回答什么问题、在什么环境里跑、什么时候跑、哪些没做以及为什么。dev-workflow 3.5 把测试按 scaffold skill 的 `shared/testing.md` 分成静态检查、单元、组件、集成、端到端、快照、交付和非功能，并要求每个项目说明用了哪些、没用哪些。

## 决策

按 `shared/testing.md` 的七个问题，本项目用这些种类：

| 种类   | 为什么用                                            | 环境                                                                                         |
| ------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 单元   | api、libs、web 和工具脚本都有自己的规则和计算       | 测试进程内                                                                                   |
| 组件   | web 有孩子和家长的界面                              | jsdom 和 Testing Library                                                                     |
| 集成   | api 读写 PostgreSQL，还接邮件和 AI                  | 每次运行一个临时 postgres:17-alpine 容器，和 CI 同一镜像；邮件和 AI 用假的或进程内测试服务器 |
| 端到端 | 注册、登录、做题这些流程跨页面和服务器              | 构建后的站点、6 个 API 服务、临时数据库；打包镜像的双实例编排另跑一套                        |
| 快照   | 页面和部件的样子用几条断言说不清                    | 固定版本的官方 Playwright 镜像，三个视口                                                     |
| 交付   | 服务部署到 staging，数据跨版本靠迁移                | 打包镜像和迁移在独立的 Compose 项目里验证；合并后发布到 staging 并跑 smoke                   |
| 非功能 | 需求有无障碍目标（WCAG AA、触摸目标），数据涉及儿童 | 无障碍检查在快照套件里；线上依赖的高危漏洞在每个 PR 扫描，完整扫描每周一次                   |

不做的部分：

- 性能（普通操作 2 秒、AI 5 秒开始响应）：维护者没有目标网络的设备，CI 和开发机测出的数不能代表孩子的网络，上线后观察。
- 负载（三个孩子同时学习）：需求的目标还没定。
- 从上一个发布的数据升级：还没有正式发布，放在发布前。

每个重型种类各有一个项目命令，自己准备和清理临时环境，端口能配置；CI 各有一个 job（集成是 database，端到端是 app，快照和无障碍是 visual，打包和迁移是 accounts，依赖漏洞是 security）。依赖漏洞的结果会随新公告变化，不随我们的改动变化，所以 PR 只拦线上依赖里的 high 和 critical，其余由每周的 dependency-audit 开 issue。端到端在 CI 里用 Chromium 桌面、Chromium 模拟 iPhone 13 和 WebKit 三种环境，不加环境矩阵；真机 iPad 和 iPhone 的 Safari 放在发布前。

## 被否决的方案

- **数据库测试留在 app job 里**：集成和端到端混在一个 job，谁失败要看日志才知道，也不能并行。
- **每个 PR 跑完整的 npm audit**：开发依赖的中危公告和本次改动无关，会让不相干的 PR 失败。
- **用 CI 的海外 runner 定时测响应时间**：测出的数不是孩子的网络，不能当证据。

## 后果

CLAUDE.md 的「测试」一节列出每个种类的命令、占用、每次提交前和开 PR 前跑什么，以及改动的目录对应哪些测试。新加一种外部服务、发布正式版本或定下负载目标时，重新看这张表。
