# ADR-0005 事务、草稿与模型反馈隔离

- 状态：草稿保留策略已接受；#29 的一致性与恢复方案待维护者决定
- 日期：2026-11-04
- 相关需求：REQ-002、004、005、006、008、009

## 背景与候选

家庭注册不能出现重复兑换，AI 重试不能重复累计进度。候选为应用内存管理、数据库事务或多服务最终一致性；试点规模使用 PostgreSQL 事务最直接，不需要消息队列。

## 决策提议

KEY 消费与创建儿童同事务；作答请求 ID 按儿童与题目版本唯一；进度由已提交作答和提示事件更新，AI 文本不能直接写入“掌握”。草稿带版本，冲突显式返回。一次有帮助的作答不能同时记作独立成功。

AI 调用在数据库事务之外，避免等待外部服务期间持有事务；先持久化请求与必要额度预留，再调用、结算并写入经过校验的反馈状态。取消不保证供应商不收费，供应商失败和未知计费结果要可追踪，不自动无限重试。

用户确认草稿最后编辑后 7 天过期，提交或放弃时清除；不保存原始音频。绘图仅为暂存草稿，按已确认的 7 天期限管理。进度摘要保留到家庭删除。家庭删除需撤销会话、删除当前数据并按明确备份期限淘汰备份；恢复旧备份时应用删除清单，不能使已删除家庭重新可登录。实际备份位置、期限、清单最少内容和销毁方式待部署设计确定。

## 作答与多设备草稿提议

- 请求由客户端生成作答 ID，超时后保留 ID 与原输入重试。服务端以儿童、题目版本和作答 ID 建立唯一约束，在同一事务内写入作答、更新进度并清理该次提交对应的草稿版本。重复请求返回原回执，同 ID 换内容返回冲突。已结束的请求重试不清理之后创建的草稿。
- 草稿保存与放弃比较客户端所见版本。版本过期或变动时，服务端返回当前版本或缺失，客户端保留本地输入，让儿童显式选择。重新创建草稿使用新的版本令牌。恢复旧备份后更换服务端数据世代，旧设备的待提交和待保存请求先与服务器核对，防止自动覆盖或重放失去回执的 AI 请求。
- 用量状态不明时，保守限制新调用并允许引导教学。作答回执和 AI 额度账本分别处理重试。数据库事务只保护自身提交，供应商对重复请求和未知计费结果的行为由 #39 验证。

## 家庭删除与恢复提议

| 项目 | 试点提议 | 验收方式 |
| --- | --- | --- |
| 备份 | 每日加密备份，独立存储，保留 14 天 | 用备份清单核对可恢复副本和到期销毁，覆盖自动快照、手工导出和其他副本 |
| RPO | 普通业务数据最多丢失 24 小时，已受理家庭删除清单必须完整可恢复 | 比对故障时刻、可用备份的数据时点及独立删除清单的连续性 |
| RTO | 从宣告需恢复到通过完整性检查并重新开放服务，目标 4 小时 | 在目标环境从实际备份位置计时演练 |
| 在线删除 | 受理时阻断家庭登录与写入并撤销旧会话，24 小时内完成在线数据清理 | #44 验证重试、旧会话、并发写入和部分失败，覆盖绘图、导出及待执行任务 |
| 删除清单 | 仅保留不可复用的内部家庭 ID、删除时点及重放顺序，放在应用备份之外并独立保护 | 清单条目至少保留到所有可能包含该家庭的可恢复副本均已核实淘汰，届时可销毁。不可用或无法证明完整时维持关闭 |

1. 在线受理删除前，将删除意图持久化到独立清单，并确保应用所有实例已拒绝该家庭的登录、旧会话和写入。任一步失败须保留待处理状态并可继续处理。在线清理成功后再标记完成。
2. 恢复前隔离目标库、停止应用接入和后台任务，并隔离旧写入端。使用独立于备份的就绪门槛。恢复库在同步删除记录期间禁止应用连接。
3. 从权威清单取得覆盖所选备份至恢复切换的记录，校验来源、范围、连续性和最终水位。在打开服务前冻结相关写入并完成最后增量核对。幂等清除标记家庭的行、会话、绘图、导出和队列，并按恢复时点移除过期草稿。正式演练需验证跨存储清理以及删除清单写入与切换之间没有空档。
4. 核对已删家庭及其旧会话均不可访问、其他家庭的数据可用，再开放服务。清单缺失、重放中断或核对失败时保持关闭。打开前确认任务和会话策略与恢复后的数据世代一致。

备份位置与访问控制、实际副本的删除能力、清单防篡改与独立持久性、删除/恢复目标和告警流程待维护者确认并由 #44/#45 实测。14 天、24 小时和 4 小时均为提议。按已确认规则，草稿最后编辑后 7 天过期。

PostgreSQL 的 Read Committed 行为允许唯一约束等待并发事务，再在后续语句读取已提交回执。使用 `pg_dump -Fc` 将应用库备份为可恢复归档，删除清单由另一数据库提供。[PostgreSQL 事务隔离](https://www.postgresql.org/docs/17/transaction-iso.html) · [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)

## 探针证据

- PostgreSQL 17.11 上，三轮各有两个并发重试实际等待锁。每轮最终只有一条作答和一次进度累计，两个并发重试与一次模拟丢失响应后的重试均取到相同回执。注入事务错误后，作答和进度均未保留，随后重试成功。
- 同一草稿版本的两个保存请求中，一个成功，一个拿到当前版本及冲突。提交清除了原草稿，重试保留了随后新建的草稿。
- 旧备份确实包含后来删除的家庭、其会话和过期草稿。清单不可用、缺项或重放回滚时，应用角色的数据库连接仍被拒绝。两次完整重放结果一致。开放后只剩未删除家庭的会话、作答和有效草稿。

原库、独立清单库和恢复库在本机同一个容器内。生产认证、异地备份、清单存储故障域和服务恢复时间由 #44/#45 验证。运行命令和原始日志见 [#29 探针记录](../../spikes/answer-consistency-recovery/SPIKE.md)。
