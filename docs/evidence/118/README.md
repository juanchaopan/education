# #118 新版本发布后先保存草稿再刷新

状态：已实现，本机检查通过。需要隔离数据库的浏览器检查由 CI 运行。在真实 staging 上跨两次发布的验收，要等合并后的两次发布完成才能做，列在文末。做法依据 [ADR-0009 发布更新与草稿保护](../../adr/0009-account-security-spike.md#发布更新与草稿保护) 和 [ADR-0006](../../adr/0006-delivery-environments.md)。

## 做法

- **页面的版本**：`npm run build:staging` 带着 `RELEASE_SHA` 构建，Vite 插件把这个 SHA 写进页面的 `<meta name="education-release">`；`/version.json` 报的是同一个 SHA。staging 冒烟检查要求两者都等于这次的 SHA，并要求页面响应头是 `no-cache`。本地构建没有这个 meta，页面也就不检查版本。
- **什么时候检查**：页面可见时每 60 秒检查一次，在后台不检查；恢复可见、获得焦点、恢复网络时立刻检查。请求带 `cache: 'no-store'`。请求失败，或者回复里不是 40 位十六进制的版本号，都不刷新，按 1、2、4、8 分钟退避重试，最长间隔 15 分钟。版本相同时继续每 60 秒检查。
- **页面上谁会被刷新影响**：
  - 草稿：未同步，或者冲突中保留着的编辑，算“未保存”；正在保存，算“保存中”。
  - 课程短片：老师在讲话时（句与句之间的停顿也算）算“播放中”。孩子暂停了，或者某句话没放出来、在等孩子重听，不算播放中。
- **发现新版本以后**：
  - 课程页上的短片正在播放时先不动，因为刷新会打断旁白，孩子还得重新点“开始”才有声音（维护者的要求）。孩子离开课程页，或者短片安静下来以后，才继续往下走。课程以外的页面不用等。
  - 有未保存的草稿就先保存。保存失败、离线或冲突时保留原输入，显示“更新已准备好，保存后将自动更新。”。之后每次检查都会再试一次保存；孩子自己点保存成功、或者到下一幕自动保存成功，也算数。
  - 全部保存好以后完整刷新。刷新不碰 cookie，所以登录还在。
- **每个版本只自动刷新一次**：刷新前把目标版本记进这个标签页的 sessionStorage，页面加载时读出来。如果服务端报的版本正是上次刷新时的目标，而页面还不是它，说明缓存没同步或者回滚后拿到的还是旧页面。这时不再自动刷新，只显示“新版本还没准备好。刚才做的和登录都还在。”和“再试一次”按钮。sessionStorage 不能用的标签页从不自动刷新，只显示这个提示。
- **回滚**：服务端报的版本只要和页面不同，就按同样的流程处理。
- **旧资源不可用**：课程文件没加载出来时，页面不再整页空白，而是显示“这道题没有打开”和“再试一次”（孩子点了才刷新），同时立刻检查一次版本。

## 改动的位置

| 位置                                                                         | 内容                                                                     |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `apps/web/vite.config.ts`、`scripts/staging-smoke.mjs`                       | 页面 meta 里写版本；冒烟检查页面和版本文件是否一致                       |
| `apps/web/src/shared/lib/reload-readiness.ts`、`ReloadReadinessProvider.tsx` | 页面各部分报告刷新会不会丢东西，按“播放中、未保存、保存中”的优先顺序汇总 |
| `apps/web/src/features/learning/data-access/useLessonDraft.ts`               | 草稿报告未保存或保存中，按页面要求保存                                   |
| `apps/web/src/features/learning/interaction/useLessonFilm.ts`                | 短片报告是否在播放（`playing`）                                          |
| `apps/web/src/app/release/`                                                  | 读页面版本、请求版本文件、一次刷新的记录、检查和刷新的流程、更新提示     |
| `apps/web/src/app/LessonRoute.tsx`、`LessonBoundary.tsx`                     | 课程加载失败时的重试                                                     |

- `npm run format:check`、`npm run lint`、`npm run arch`、`npm run typecheck`：通过。
- `npm test -w @education/web`：53 个文件、248 个测试通过。`npm run test:staging`：53 个测试通过。
- `npm run build`：通过。
- 浏览器检查：在本机手动起 6 个 API 服务后运行全部 e2e，37 个通过，36 个跳过（需要 `DATABASE_URL`），0 个失败。其中 `release-update.spec.ts` 在桌面和手机两个项目里各 5 个通过、各 2 个跳过（需要数据库）。
- `npm run test:visual -- --update --workers=1`（Docker）：553 个通过，101 个跳过；只新增了更新提示的 6 张基准截图。
- 用 `RELEASE_SHA` 构建时，`apps/web/dist/index.html` 里有对应的 meta；不带 `RELEASE_SHA` 构建时没有。
- API 的代码没有改动。本机在其他任务并行运行时跑全部 API 单元测试，13 个测试在每个文件的第一个请求处超过 5 秒超时；单独运行 `src/app.test.ts` 时 9 个全部通过。以 CI 为准。`npm run test:db` 和 `npm run test:toolchain` 没有在本机运行，也以 CI 为准。

## 未完成和范围外

- 普通表单（家长和孩子的登录、注册，家长空间里的各个表单）不算未保存输入。填到一半时遇到更新，刷新后内容会丢。维护者决定作为后续事项处理。
- 草稿冲突时，更新会一直等孩子选择保留哪一份，期间显示“更新已准备好，保存后将自动更新。”。
- 真实 staging 上的验收：合并后再等一次发布，在已打开的 staging 页面上确认会自动更新、登录还在、不会循环刷新；并核对 Vercel 删除旧资源后，课程文件加载失败时显示的重试。这两次发布由手动流程触发，本记录不声称已经完成。
